# 06 · 高可用与可靠性

## 6.1 设计原则
> 高可用 ≠ 上多少机器，而是：**关键路径无单点、故障可降级、行为可幂等、状态可恢复**。

## 6.2 机制清单
| 机制 | 方案 |
|---|---|
| 无单点 | 应用无状态可扩；MySQL 主从（半同步）；Redis 主从/哨兵 |
| 调度防重 | Celery Beat 单点 + Redis 分布式锁（唯一 task_id）|
| 异步解耦 | 长任务全走队列 |
| 幂等 | 唯一键 + 乐观锁 + Idempotency-Key |
| 降级 | LLM→规则；采集 API→浏览器；AI 失败不阻塞投递 |
| 重试 | 指数退避 + 抖动，有限次 |
| 熔断 | 采集/LLM 每路熔断器（CLOSED/OPEN/HALF-OPEN）|
| 备份 | MySQL 全量+binlog 增量；对象存储版本 |

## 6.3 降级链
```
LLM 挂 → 规则+向量匹配（w1+w2）→ 投递不阻塞
采集 API 挂 → 浏览器 fallback → 仍失败 → 退避重试 → 告警
浏览器池满 → 排队等待，不崩溃
验证码 → NEEDS_HUMAN 人工介入
```

## 6.4 熔断器（circuit breaker）
- 每平台每方式一个状态：CLOSED（正常）/ OPEN（熔断）/ HALF-OPEN（探测）
- 失败率超阈值 → OPEN，暂停该方式
- 定时探活 → 恢复 → CLOSED

## 6.5 备份与恢复
- MySQL：每日全量 + binlog 增量
- 恢复演练：定期验证备份可恢复
- 对象存储：简历文件多版本

## 6.6 扩展路径
```
单机(docker-compose) → 应用多实例+LB → worker扩容 → DB主从 → 分库分表
```
- 应用无状态是水平扩展的前提
- 有状态部分（浏览器池/调度）独立出来，单独扩容
