## 12.2 本机限制判断

### 12.2.1 主要限制

1. **内存上限是第一限制**：总内存 16 GB，当前可用仅约 3.67 GB。若同时运行 Docker、MySQL、Redis、前端、后端、FAISS、Ollama、Playwright，容易卡顿或 OOM。
2. **显存只能支持轻量 AI**：RTX 2060 6 GB 适合 embedding、小型量化模型，不适合大参数 LLM 长时间并发。
3. **当前缺 Docker/Ollama/WSL 发行版**：不能直接按完整 Docker Compose 方案启动。
4. **项目盘空间偏紧**：`I:` 盘只剩约 34.54 GB，模型、索引、数据库 volume 不宜放这里。
5. **Node 版本偏新**：Node 24 可用，但 Vue/Vite/依赖生态通常对 LTS 版本兼容更稳，建议后续使用 Node 22 LTS 或通过 nvm-windows 管理。

### 12.2.2 可以稳定支持的能力

当前机器适合：

1. FastAPI 后端开发。
2. Vue 前端开发。
3. MySQL/Redis 本地轻量运行，或先用 SQLite 替代。
4. 小规模岗位数据导入。
5. 小规模 FAISS 向量检索。
6. pytest 单元测试和集成测试。
7. 单个 Playwright 浏览器实例调试。
8. 使用 CPU 或轻量 GPU 做 embedding。

当前机器不建议同时做：

1. 本地大语言模型推理。
2. 多浏览器实例池。
3. 大规模 FAISS 索引常驻内存。
4. Docker Desktop + Ollama + Playwright + 前后端全开。
5. 多平台自动化采集长时间运行。

## 12.3 推荐实施方案

### 12.3.1 总体策略

本机应采用“轻量 MVP 优先，重型能力外置或后置”的方案。

推荐路线：

```text
第一阶段：Windows 原生开发
  → FastAPI + SQLite/本地文件 + FAISS 小索引 + pytest

第二阶段：补齐容器环境
  → 安装 WSL2 Ubuntu + Docker Desktop
  → MySQL + Redis + MinIO 容器化

第三阶段：启用 AI 能力
  → 优先 embedding
  → LLM 解释可先用远程 API 或延后
  → 本地 Ollama 只跑小模型或 embedding

第四阶段：受控浏览器辅助
  → 单浏览器实例调试
  → 不在本机跑多账号、多实例浏览器池
```

### 12.3.2 MVP 本机推荐架构

```text
Vue dev server
  → FastAPI
    → SQLite / MySQL
    → FAISS 本地小索引
    → 本地 embedding 服务或离线 embedding 脚本
    → pytest 测试
```

MVP 不强依赖 Docker。先把推荐匹配闭环做出来：

1. 岗位 CSV/JSON 导入。
2. 岗位清洗和去重。
3. 简历和偏好解析。
4. embedding 生成。
5. FAISS 检索。
6. 规则过滤。
7. 推荐理由。
8. 用户反馈影响排序。
9. 人工投递记录。

## 12.8 本机推荐开发顺序

### 第一步：建立 Git 与文档基线

目标：

1. 初始化 Git。
2. 提交 `docs` 文档。
3. 建立后续阶段分支。

验收：

1. `git status` 干净。
2. README 能索引所有文档。
3. 架构检查报告和本机方案已提交。

### 第二步：先做无 Docker MVP

目标：

1. 后端 FastAPI 骨架。
2. SQLite 数据库。
3. pytest + ruff。
4. CSV/JSON 岗位导入。
5. 规则过滤。

原因：

1. 当前 Docker 不可用。
2. 本机内存有限。
3. 先验证业务闭环比先搭重型环境更稳。

### 第三步：加入向量检索

目标：

1. 本地 FAISS 小索引。
2. embedding 生成脚本。
3. 固定样本 golden test。
4. 向量索引 manifest。

限制：

1. 岗位数量先控制在 10,000-50,000。
2. 不先上大规模向量数据库。

### 第四步：补 Docker 与服务化组件

目标：

1. 安装 WSL2 Ubuntu。
2. 安装 Docker Desktop。
3. 将 MySQL、Redis、MinIO 容器化。
4. 将 SQLite 迁移到 MySQL。

限制：

1. Docker 内存限制在 6-8 GB。
2. volume 放 `D:` 或 `H:`。

### 第五步：谨慎加入 AI 与浏览器

目标：

1. embedding 优先。
2. LLM 解释后置。
3. Playwright 只开单实例调试。

限制：

1. 不跑多浏览器池。
2. 不在本机训练模型。
3. 不把本地 LLM 作为核心链路硬依赖。

## 12.9 本机预期结果

在当前配置下，合理目标是完成“推荐匹配 MVP”，而不是完整生产级自动化中台。

### 可达到

1. 本地启动后端和前端。
2. 导入岗位数据。
3. 根据简历和偏好生成推荐。
4. 展示匹配分与理由。
5. 用户反馈影响排序。
6. 记录人工投递状态。
7. 运行单元测试与集成测试。
8. 小规模 FAISS 检索。

### 谨慎达到

1. Docker Compose 全套组件。
2. Ollama embedding。
3. 单实例 Playwright 调试。
4. MySQL/Redis/MinIO 本地容器化。

### 不建议本机承担

1. 多浏览器并发采集。
2. 本地大模型 LLM 长时间推理。
3. 大规模岗位索引常驻。
4. 生产级 HA 验证。
5. 多账号自动化投递。

## 12.10 最终方案

建议采用以下方案：

```text
阶段 1：Windows 原生轻量 MVP
  FastAPI + SQLite + FAISS CPU + pytest + Vue

阶段 2：Docker 化基础设施
  WSL2 Ubuntu + Docker Desktop + MySQL + Redis + MinIO

阶段 3：AI 增强
  embedding 本地化，LLM 解释可选，用户反馈学习上线

阶段 4：自动化能力试验
  单浏览器实例，人工确认，不做大规模自动投递
```

这台机器的最佳使用方式是：用 CPU 和 16 线程支撑开发、测试和小规模向量检索；用 RTX 2060 6GB 支撑轻量 embedding；把重型模型、多浏览器池和生产级高可用放到后续阶段或外部环境。这样推进，性能、稳定性和开发节奏会比较舒服。
