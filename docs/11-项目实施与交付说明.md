# 11 · 项目实施与交付说明

> 项目：job-apply 求职自动化系统  
> 编写日期：2026-08-17  
> 用途：说明项目架构、Git 提交阶段、验收测试、预估周期、资源需求、设备限制与预期结果

## 11.1 项目定位

本项目定位为“AI 辅助的半自动求职推荐与投递记录系统”。系统核心价值不是直接替用户大规模自动投递，而是帮助用户持续发现更匹配的岗位，解释岗位与个人简历、偏好之间的匹配关系，并记录投递过程与结果。

MVP 阶段建议聚焦：

1. 岗位数据导入或低风险采集。
2. 岗位标准化与去重。
3. 简历、自然语言偏好、岗位 JD 的向量化。
4. 规则过滤 + 向量召回 + 推荐解释。
5. 用户反馈驱动的偏好学习。
6. 人工确认投递与投递漏斗报表。

暂不建议在 MVP 阶段承诺：

1. 多平台全自动采集。
2. 自动提交投递。
3. 高可用无单点。
4. 大规模分布式向量检索。
5. 复杂 LLM 微调。

## 11.2 目标架构说明

### 11.2.1 逻辑架构

```text
前端 Vue3
  ├ 岗位列表与筛选
  ├ 推荐解释与匹配分
  ├ 用户偏好配置
  ├ 投递记录与漏斗报表
  └ 人工确认与反馈入口

后端 FastAPI
  ├ 用户与偏好服务
  ├ 岗位服务
  ├ 匹配服务
  ├ 投递记录服务
  ├ 报表服务
  └ 任务服务

异步任务
  ├ 岗位导入/采集任务
  ├ embedding 生成任务
  ├ 向量索引构建任务
  ├ 偏好画像更新任务
  └ 报表预聚合任务

数据层
  ├ MySQL：结构化业务数据
  ├ Redis：缓存、限流、短期任务状态
  ├ FAISS/pgvector：岗位向量索引
  └ MinIO/本地对象存储：简历文件与索引快照
```

### 11.2.2 核心业务链路

```text
岗位数据进入系统
  → 清洗与标准化
  → 去重入库
  → 生成岗位 embedding
  → 建立向量索引

用户上传简历 / 输入偏好
  → 生成简历向量
  → 生成偏好向量
  → 合成用户画像向量

推荐匹配
  → 规则硬过滤
  → 向量召回 top-N
  → 结构化规则打分
  → LLM 生成解释
  → 用户查看、收藏、投递或标记不感兴趣

用户反馈
  → 写入反馈表
  → 更新行为偏好向量
  → 影响下一轮推荐排序
```

## 11.3 Git 提交阶段规划

| 阶段 | 分支建议 | 提交内容 | 主要产物 |
|---|---|---|---|
| S0 文档基线 | `docs/architecture-baseline` | 架构文档、检查报告、实施说明 | `docs/01-11` |
| S1 项目骨架 | `feat/bootstrap` | FastAPI/Vue 目录、配置、CI、基础测试 | 可启动空服务 |
| S2 数据模型 | `feat/data-model` | SQLAlchemy 模型、Alembic 迁移、核心表 | 可迁移数据库 |
| S3 岗位导入 | `feat/job-ingestion` | 岗位导入、标准化、去重、数据校验 | 岗位可入库 |
| S4 匹配引擎 | `feat/matching-engine` | 规则过滤、embedding、向量召回、评分 | 推荐结果可返回 |
| S5 偏好学习 | `feat/preference-learning` | 用户反馈、行为权重、画像更新 | 反馈影响排序 |
| S6 投递记录 | `feat/application-workflow` | 人工投递记录、状态机、幂等 | 投递状态可追踪 |
| S7 报表看板 | `feat/report-dashboard` | 漏斗报表、趋势统计、前端看板 | 可视化结果 |
| S8 异步可靠性 | `feat/async-tasks` | Celery/RabbitMQ、重试、任务状态、trace_id | 任务可恢复 |
| S9 安全与部署 | `feat/security-deploy` | 鉴权、脱敏、Docker Compose、部署文档 | 可本地部署 |

提交粒度建议：

1. 一个提交只解决一个清晰问题。
2. 数据库迁移与模型代码放在同一阶段。
3. 每阶段必须包含对应测试。
4. 不把前端大改、后端大改、数据库迁移混在一个提交里。
5. 每个阶段合并前必须通过本阶段验收。

推荐提交命名：

```text
docs: add delivery plan and resource estimate
chore: bootstrap backend service
feat: add core database models
feat: add job ingestion pipeline
feat: add matching engine
feat: add preference learning
feat: add application state machine
test: add matching engine unit tests
```

## 11.7 预估资源与内存

### 11.7.1 开发环境最低配置

| 资源 | 最低配置 | 说明 |
|---|---:|---|
| CPU | 4 核 | 可运行后端、数据库和基础 embedding |
| 内存 | 8 GB | 仅适合轻量开发，不建议同时跑大模型和浏览器池 |
| 磁盘 | 20 GB 可用 | 存放依赖、MySQL、Redis、少量岗位数据 |
| GPU | 非必需 | MVP 可用 CPU embedding 或远程服务 |
| 系统 | Windows + WSL2 或 Linux | Playwright 在 Linux 容器中更稳定 |

### 11.7.2 推荐开发配置

| 资源 | 推荐配置 | 说明 |
|---|---:|---|
| CPU | 8 核以上 | embedding、索引构建、异步任务更顺 |
| 内存 | 16-32 GB | 推荐 32 GB，便于同时跑 Docker、FAISS、Ollama |
| 磁盘 | 50-100 GB 可用 SSD | 模型、索引、日志、数据库增长较快 |
| GPU | 6-12 GB 显存，可选 | 本地 LLM 推理更流畅 |
| 网络 | 稳定即可 | 若使用远程 embedding/LLM，需要考虑 API 延迟和费用 |

### 11.7.3 单机 Docker Compose 内存估算

| 组件 | MVP 内存 | 增强版内存 | 说明 |
|---|---:|---:|---|
| FastAPI | 200-500 MB | 500 MB-1 GB | 取决于 worker 数和依赖 |
| Vue dev server | 200-500 MB | 200-500 MB | 生产构建后更低 |
| MySQL | 512 MB-1 GB | 1-2 GB | 岗位量增长后需提高 buffer |
| Redis | 128-512 MB | 512 MB-1 GB | 不建议长期存大对象 |
| Celery worker | 300 MB-1 GB | 1-3 GB | embedding/Playwright 会显著增加 |
| FAISS 索引 | 100 MB-1 GB | 1-4 GB | 与岗位数量、向量维度、索引类型相关 |
| MinIO | 128-512 MB | 512 MB-1 GB | 简历、索引快照、附件 |
| Ollama embedding | 2-6 GB | 6-12 GB | 取决于模型 |
| Playwright 浏览器 | 300-800 MB/实例 | 300-800 MB/实例 | 浏览器池是资源大户 |

推荐内存：

| 运行模式 | 建议内存 |
|---|---:|
| 文档 + 后端骨架 | 8 GB |
| MVP：API + MySQL + Redis + 基础匹配 | 16 GB |
| 推荐本地开发：加 FAISS + Ollama embedding | 32 GB |
| 加 Playwright 浏览器池 + 本地 LLM | 32-64 GB |

### 11.7.4 FAISS 内存粗估

假设使用 `bge-m3`，向量维度按 1024 估算，float32 每维 4 字节。

```text
单条岗位向量 ≈ 1024 * 4 = 4096 bytes ≈ 4 KB
10,000 岗位 ≈ 40 MB
100,000 岗位 ≈ 400 MB
```

实际 FAISS 索引还会有额外结构开销，建议按 2-4 倍预留：

| 岗位数量 | 原始向量 | 建议预留 |
|---:|---:|---:|
| 10,000 | 约 40 MB | 100-200 MB |
| 50,000 | 约 200 MB | 500 MB-1 GB |
| 100,000 | 约 400 MB | 1-2 GB |

MVP 若岗位量小于 50,000，FAISS 单机足够。超过 100,000 后应评估 pgvector、Qdrant 或 Milvus。

## 11.8 设备限制与降级策略

### 11.8.1 8 GB 内存设备

建议范围：

1. 不运行本地 LLM。
2. 不运行 Playwright 浏览器池。
3. embedding 可使用远程 API 或离线批处理。
4. MySQL、Redis 使用较小配置。
5. FAISS 仅加载小规模索引。

可交付能力：

1. 后端 API。
2. 岗位导入。
3. 规则过滤。
4. 小规模向量召回。
5. 投递记录。

### 11.8.2 16 GB 内存设备

建议范围：

1. 可运行完整 MVP。
2. 可运行小模型 embedding。
3. 可运行单个 Playwright 实例用于开发验证。
4. 不建议同时运行本地大语言模型和多浏览器实例。

可交付能力：

1. 推荐 MVP。
2. 用户偏好学习。
3. 基础报表。
4. 小规模异步任务。

### 11.8.3 32 GB 以上设备

建议范围：

1. 可运行 Docker Compose 完整开发环境。
2. 可运行 Ollama embedding。
3. 可运行 FAISS 中等规模索引。
4. 可运行少量 Playwright 浏览器实例。

可交付能力：

1. 完整本地开发。
2. 异步任务和索引构建。
3. 推荐解释。
4. 受控浏览器辅助验证。

## 11.9 预期结果

### 11.9.1 MVP 预期结果

MVP 完成后，系统应能做到：

1. 导入或采集一批岗位数据。
2. 将岗位清洗成统一结构。
3. 对岗位生成 embedding 并建立向量索引。
4. 读取用户简历和自然语言偏好。
5. 返回岗位推荐列表、匹配分和推荐理由。
6. 记录用户点击、收藏、投递、不感兴趣等反馈。
7. 根据反馈调整后续推荐排序。
8. 人工记录投递状态。
9. 展示投递漏斗和基础统计。

### 11.9.2 可量化验收指标

| 指标 | MVP 目标 |
|---|---:|
| 岗位导入成功率 | >= 95% |
| 重复岗位去重准确率 | >= 99% |
| 推荐接口响应时间 | 小于 2 秒，不含首次索引构建 |
| 匹配结果稳定性 | 同一输入返回一致排序 |
| 用户反馈生效时间 | 小于 5 分钟 |
| 状态机非法流转拦截率 | 100% |
| 单元测试通过率 | 100% |
| 核心模块测试覆盖率 | >= 70% |

### 11.9.3 用户可感知结果

用户最终应看到：

1. 哪些岗位值得优先投。
2. 为什么这个岗位匹配。
3. 哪些技能、语言、经验满足要求。
4. 哪些条件不满足或存在风险。
5. 系统会逐步理解用户偏好。
6. 投递后能看到漏斗变化和反馈统计。

## 11.10 不纳入 MVP 的内容

以下能力不建议作为第一阶段交付目标：

1. 多平台深度反爬采集。
2. 自动提交岗位投递。
3. 验证码自动识别。
4. LLM 模型微调。
5. 分布式高可用部署。
6. 多账号自动轮换。
7. 大规模向量数据库集群。

这些能力可以作为后续增强，但必须先完成合规评估、账号风险评估和故障恢复设计。

## 11.12 总结

项目应按“推荐匹配闭环优先，自动化能力后置”的方式推进。第一阶段先交付稳定可解释的岗位推荐、用户偏好学习和人工投递记录；第二阶段再增强异步任务、可观测和报表；最后才考虑多平台自动化和高可用。

最小可行成功标准：

```text
用户输入简历和偏好
  → 系统推荐岗位
  → 给出匹配理由
  → 用户反馈喜好
  → 下一轮推荐变得更贴近用户
  → 投递过程可记录、可统计、可回顾
```

只要这条闭环跑通，项目就已经具备真实使用价值。
