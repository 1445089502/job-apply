# 10 · 架构检查报告

> 项目：job-apply 求职自动化系统  
> 检查日期：2026-08-17  
> 检查角色：架构检查师  
> 检查范围：总体架构、数据采集、岗位匹配、自然语言向量检索、AI 自学习、异步任务、数据模型、高可用、安全合规、部署落地

## 10.1 检查结论

当前架构已经具备较完整的分层意识：接入层、业务层、异步层、数据层、可观测与部署层边界基本清晰；也覆盖了求职自动化系统的核心链路：岗位采集、岗位标准化、筛选匹配、半自动投递、投递状态追踪与报表。

但从架构落地角度看，当前设计仍处于“概念完整、工程闭环不足”的阶段。主要问题集中在四类：

1. 合规边界与采集/投递自动化能力存在冲突。
2. 高可用目标与 Celery Beat、Redis、FAISS 等实际选型存在落差。
3. 异步任务、幂等、外部平台投递副作用没有形成严格一致性闭环。
4. 自然语言向量检索与 AI 自学习方向正确，但缺少向量生命周期、偏好反馈、模型版本和可解释性设计。

总体评级：

| 维度 | 评级 | 说明 |
|---|---|---|
| 架构方向 | B+ | 分层合理，核心能力覆盖完整 |
| 工程可落地性 | B- | 关键机制仍偏口号，需要补充状态、表、边界和故障模型 |
| 高可用可靠性 | C+ | 声明“无单点”，但 Beat、Redis、FAISS、浏览器池仍有单点或状态风险 |
| 安全合规 | C | 已意识到 PIPL 和平台条款，但缺少可执行约束 |
| AI 匹配设计 | B | 检索增强方向正确，需补偏好学习和评估闭环 |
| MVP 可行性 | B | 若收缩自动投递和 HA 目标，可以落地 |

## 10.2 风险等级定义

| 等级 | 含义 | 处理要求 |
|---|---|---|
| P0 | 阻断性风险 | 不解决不得进入实现或上线 |
| P1 | 高风险 | 必须在核心链路开发前完成设计修正 |
| P2 | 中风险 | MVP 可接受，但必须记录约束和后续计划 |
| P3 | 低风险 | 可作为优化项排期 |

## 10.3 核心问题清单

| 编号 | 等级 | 领域 | 问题 | 建议 |
|---|---|---|---|---|
| A-01 | P0 | 合规 | 文档同时声明遵守平台条款，又设计 API 逆向、反检测、登录态持久化、验证码人工介入 | 明确平台能力白名单，优先官方 API、用户授权导出、人工辅助；禁止不合规自动化 |
| A-02 | P1 | 高可用 | “无单点”与 Celery Beat 单点调度矛盾 | 将目标改为“单机可恢复”，或引入 leader election、任务租约和 fencing token |
| A-03 | P1 | 异步一致性 | Celery + Redis/RabbitMQ 只能保证至少一次执行，不能保证只执行一次 | 按 at-least-once 设计，外部副作用靠业务幂等和状态机兜底 |
| A-04 | P1 | Redis | Redis 同时承担队列、锁、限流、会话、登录态，故障域过大 | 生产拆分 broker、cache/session、lock/rate-limit，MVP 明确接受单点风险 |
| A-05 | P1 | 投递状态机 | 状态不足以表达外部平台未知结果、取消、重复、人工超时 | 补充 UNKNOWN、CANCELLED、DUPLICATE、HUMAN_TIMEOUT、SUBMITTED_UNCONFIRMED 等状态 |
| A-06 | P1 | 数据模型 | 缺少 platform_account、idempotency_request、task_execution、vector_index_manifest 等核心表 | 扩充数据模型，显式表达平台账号、幂等请求、任务执行、向量索引版本 |
| A-07 | P1 | 向量检索 | FAISS 索引持久化、热更新、删除、模型版本、回滚机制缺失 | 建立向量索引 manifest、embedding_version、重建任务和快照机制 |
| A-08 | P1 | AI 自学习 | 用户反馈未进入匹配闭环 | 增加 user_job_feedback、user_preference、behavior_embedding 设计 |
| A-09 | P2 | 评分体系 | 0.3/0.3/0.4 权重缺少依据，容易产生伪精确分 | 硬条件先淘汰，语义召回负责候选，LLM 做解释和精排，权重通过反馈校准 |
| A-10 | P2 | 安全 | Cookie、简历、日志、备份中的敏感数据删除和轮换策略不完整 | 增加 TTL、密钥轮换、日志脱敏、备份保留期、删除审计 |
| A-11 | P2 | 可观测 | 指标列表有方向，但缺少 SLO、阈值、追踪字段规范 | 定义成功率、延迟、队列积压、验证码率、投递未知率等 SLO |
| A-12 | P2 | 落地计划 | P1 同时做采集、报表、看板、筛选，若包含自动化浏览器则周期偏乐观 | MVP 先做官方/低风险数据源、手动投递记录、硬过滤和反馈闭环 |

## 10.4 自然语言转向量与检索偏向设计审查

### 10.4.1 推荐目标

匹配系统不应只回答“这个岗位和简历像不像”，还要回答：

1. 用户是否具备岗位要求。
2. 岗位是否符合用户意愿。
3. 用户近期行为是否显示出新的偏好。
4. 这个推荐结果是否可解释、可纠错、可持续学习。

因此建议将匹配架构从“简历向量 vs 岗位向量”升级为“用户画像向量 + 结构化规则 + 行为反馈”的组合。

### 10.4.2 向量对象定义

| 向量对象 | 来源 | 用途 |
|---|---|---|
| `resume_embedding` | 简历全文、项目经历、技能栈 | 表示用户能力边界 |
| `preference_embedding` | 用户自然语言偏好 | 表示用户主观意愿 |
| `behavior_embedding` | 点击、收藏、投递、不感兴趣等反馈 | 表示系统学习到的隐式偏好 |
| `job_embedding` | 岗位标题、JD、技能、公司介绍 | 表示岗位语义 |
| `query_embedding` | 用户临时搜索语句 | 支持自然语言搜索 |

推荐用户画像向量：

```text
user_profile_vector =
  0.50 * resume_embedding
+ 0.30 * preference_embedding
+ 0.20 * behavior_embedding
```

权重不是固定真理，MVP 可先用默认值，后续根据用户反馈进行校准。

### 10.4.3 检索流水线

```text
岗位采集
  → 清洗与标准化
  → 生成 job_embedding
  → 写入 MySQL + 向量索引

用户简历 / 偏好 / 搜索语句
  → 生成 resume_embedding / preference_embedding / query_embedding
  → 合成 user_profile_vector
  → 向量召回 top-N
  → SQL/规则硬过滤
  → 规则 + 向量 + LLM 精排
  → 展示综合分、命中项、缺失项、推荐理由
  → 用户反馈
  → 更新 behavior_embedding
```

### 10.4.4 检索偏向设计

检索偏向应来自三类信号：

| 信号 | 示例 | 作用 |
|---|---|---|
| 显式偏好 | “更想找 Python/FastAPI/AI 工程方向，上海或远程，不想去外包” | 直接影响召回排序 |
| 结构化偏好 | 城市、薪资、行业、公司规模、远程、语言 | 作为硬过滤或强排序因子 |
| 行为偏好 | 点击、收藏、投递、忽略、拉黑、不感兴趣 | 用于持续修正用户画像 |

反馈权重建议：

| 行为 | 权重 | 类型 |
|---|---:|---|
| 点击岗位 | +0.2 | 弱正反馈 |
| 停留查看详情 | +0.3 | 弱正反馈 |
| 收藏岗位 | +0.6 | 中正反馈 |
| 投递岗位 | +1.0 | 强正反馈 |
| 标记不感兴趣 | -0.8 | 强负反馈 |
| 拉黑公司/行业 | -1.0 | 强负反馈 |
| 投递后撤回 | -0.4 | 修正反馈 |

行为向量可先用简单公式：

```text
positive_vector = weighted_avg(用户正反馈岗位向量)
negative_vector = weighted_avg(用户负反馈岗位向量)

behavior_embedding = normalize(
  positive_vector - 0.5 * negative_vector
)
```

### 10.4.5 综合评分建议

不建议让硬过滤参与线性打分后再排序。硬过滤应先判断“能不能接受”，再进入排序。

推荐分层：

```text
第一层：硬过滤
- 城市是否接受
- 薪资是否低于底线
- 学历/经验/语言是否硬性不满足
- 公司/行业是否被拉黑

第二层：召回分
- sim(job_embedding, resume_embedding)
- sim(job_embedding, preference_embedding)
- sim(job_embedding, behavior_embedding)
- sim(job_embedding, query_embedding)

第三层：精排分
- 技能匹配
- 项目经验相关性
- 薪资匹配
- 地点匹配
- 发展方向匹配
- LLM 可解释理由
```

推荐公式：

```text
semantic_score =
  0.35 * resume_similarity
+ 0.30 * preference_similarity
+ 0.20 * behavior_similarity
+ 0.15 * query_similarity

final_score =
  0.60 * semantic_score
+ 0.25 * structured_score
+ 0.15 * llm_rerank_score
```

其中 `structured_score` 只用于软排序；硬性不满足项应直接过滤或进入人工确认队列。

### 10.4.6 AI 自学习边界

MVP 阶段不建议微调模型。应先做轻量偏好学习：

1. 不训练 embedding 模型，只更新用户偏好向量。
2. 不让 LLM 自行改规则，只让 LLM 输出理由和结构化标签。
3. 所有反馈可回滚，避免短期误点击污染长期画像。
4. 行为学习设置时间衰减，近期行为权重更高。
5. 用户可以查看和编辑偏好标签，保持可控。

时间衰减建议：

```text
effective_weight = action_weight * exp(-days_since_action / 30)
```

### 10.4.7 新增数据模型建议

```sql
CREATE TABLE user_preference (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  user_id BIGINT UNSIGNED NOT NULL,
  preference_text TEXT,
  structured_json JSON,
  resume_embedding_version VARCHAR(32),
  preference_embedding_version VARCHAR(32),
  behavior_embedding_version VARCHAR(32),
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_user (user_id)
) ENGINE=InnoDB;

CREATE TABLE user_job_feedback (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  user_id BIGINT UNSIGNED NOT NULL,
  job_id BIGINT UNSIGNED NOT NULL,
  action VARCHAR(32) NOT NULL,
  weight DECIMAL(4,2) NOT NULL,
  source VARCHAR(32) NOT NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  KEY idx_user_time (user_id, created_at),
  KEY idx_user_job (user_id, job_id)
) ENGINE=InnoDB;

CREATE TABLE job_embedding (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  job_id BIGINT UNSIGNED NOT NULL,
  model_name VARCHAR(64) NOT NULL,
  embedding_version VARCHAR(32) NOT NULL,
  vector_ref VARCHAR(255),
  content_hash VARCHAR(64) NOT NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_job_model_version (job_id, model_name, embedding_version)
) ENGINE=InnoDB;

CREATE TABLE vector_index_manifest (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  index_name VARCHAR(64) NOT NULL,
  model_name VARCHAR(64) NOT NULL,
  embedding_version VARCHAR(32) NOT NULL,
  index_path VARCHAR(255) NOT NULL,
  job_count INT NOT NULL,
  status VARCHAR(16) NOT NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  activated_at DATETIME,
  UNIQUE KEY uk_index_version (index_name, embedding_version)
) ENGINE=InnoDB;
```

## 10.5 修正后的目标架构建议

### 10.5.1 MVP 架构边界

MVP 建议收缩为：

1. 采集：只做一个低风险数据源或人工导入数据源。
2. 投递：先做“投递记录 + 人工确认”，不做全自动提交。
3. 匹配：规则硬过滤 + embedding 召回 + 简单偏好反馈。
4. AI：LLM 只做推荐理由、缺失项分析，不做自动决策。
5. HA：单机可恢复，不宣称无单点。

### 10.5.2 生产增强架构

生产阶段再补：

1. RabbitMQ 独立承担任务队列。
2. Redis 拆分为缓存/限流/会话用途。
3. Celery Beat 增加 leader election 或改用外部调度器。
4. FAISS 索引增加 manifest、快照、灰度激活、回滚。
5. 平台账号、登录态、Cookie 加密和 TTL 独立管理。
6. 完整审计日志、删除流程、备份保留期和恢复演练。

## 10.6 必须补充的架构文档

| 文档 | 内容 |
|---|---|
| 合规边界说明 | 平台能力白名单、禁止自动化动作、人工确认边界 |
| 任务一致性设计 | at-least-once、任务租约、锁 TTL、幂等请求表、外部副作用处理 |
| 投递状态机设计 | 完整状态、允许流转、异常状态、人工介入超时 |
| 向量索引生命周期 | embedding 版本、索引构建、激活、回滚、删除 |
| 偏好学习设计 | 反馈权重、时间衰减、用户可编辑偏好、画像重建 |
| 敏感数据处理 | Cookie、简历、日志、对象存储、备份中的加密与删除 |
| 可观测 SLO | 成功率、延迟、队列积压、验证码率、未知投递率 |

## 10.7 整改优先级

### P0：实现前必须明确

1. 平台合规边界。
2. 投递是否允许自动提交。
3. 用户个人数据、简历、Cookie 的存储和删除策略。

### P1：核心链路开发前完成

1. 完整投递状态机。
2. 幂等请求表和任务执行表。
3. 向量索引版本和重建机制。
4. 用户偏好与反馈数据模型。
5. Redis/RabbitMQ 职责边界。

### P2：MVP 后增强

1. LLM 精排评估集。
2. 多平台适配器统一错误码。
3. 用户偏好时间衰减。
4. 可观测指标阈值和告警规则。
5. 备份恢复演练。

## 10.8 验收标准

架构进入实现阶段前，应满足以下检查项：

| 检查项 | 验收标准 |
|---|---|
| 合规边界 | 每个平台、每个动作都有允许/禁止/人工确认说明 |
| 状态机 | 所有投递状态和异常流转可枚举、可测试 |
| 幂等 | 重复 API 请求、重复任务投递、worker 崩溃重试不会造成重复外部提交 |
| 向量检索 | embedding 模型版本、索引版本、重建和回滚流程明确 |
| 偏好学习 | 用户反馈能进入排序，且可以撤销或衰减 |
| 安全 | Cookie、简历、日志、备份均有加密、脱敏或保留策略 |
| 可观测 | 每条任务能通过 trace_id 从 API 追踪到 worker 和状态变更 |
| MVP 范围 | 不把 HA、多平台、全自动投递混入第一阶段 |

## 10.9 最终建议

建议将当前架构调整为“半自动求职推荐与投递记录系统”作为 MVP，而不是一开始就建设“多平台自动采集与自动投递中台”。先把自然语言偏好、向量召回、用户反馈学习、人工确认投递这条闭环跑通，再逐步增强采集自动化和 HA 能力。

推荐演进顺序：

```text
P1：岗位数据导入/低风险采集 → 规则过滤 → 向量召回 → 人工投递记录
P2：用户偏好向量 → 行为反馈学习 → 推荐解释 → 投递漏斗
P3：受控浏览器辅助 → 人工确认投递 → 异常状态机
P4：多平台适配 → HA 加固 → 备份恢复 → 合规审计
```

核心判断：本项目最有价值的能力不是“自动点投递按钮”，而是“理解用户想要什么，并稳定推荐值得投的岗位”。自然语言向量检索和偏好学习应该成为系统主轴，自动化采集与投递应作为受控外围能力。
